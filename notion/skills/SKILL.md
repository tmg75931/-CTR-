# 기술 블로그 글 작성 스킬

## 0. 이 스킬의 목적

프로젝트(대회·분석·모델링)를 끝낸 뒤, 그 과정을 블로그에 올릴 수 있는 형태로 정리한다.
읽는 사람은 실무자와 AI 활용에 관심 있는 사람이다. 화려한 문장보다 **직관적이고 간결한 글**이 목표다.
승혁 님의 판단 기준은 하나다: **"내가 의도한 결과물이 딱 그렇게 나오는 것."** 글이든 코드든, 의도에서 미끄러지면 실패다.

## 1. 입력으로 받아야 하는 것 (없으면 비워 두고 표시)

- 프로젝트 목적과 배경 (대회라면 주최측이 정한 지표·규칙 포함)
- 데이터 규모·형태, 전처리·연산 환경(로컬/코랩 등)
- 사용한 모델·피처·앙상블·보정 방식과 **그 선택의 이유**
- 실제 수치: 점수, 성능 지표, 소요 시간, 데이터 크기
- 막혔다가 푼 지점, 아직 아쉬운 점

> 수치가 없으면 절대 만들어 넣지 않는다. `[확인 필요: 최종 AP]` 처럼 표시하고 남긴다.

## 2. 글 구조 (기본 뼈대)

1. **문제 정의** — 무엇을 예측·해결하는 문제인가, 왜 중요한가. 2~3문단.
2. **데이터와 환경** — 규모, 제약, 연산 파이프라인. 표로 정리.
3. **접근** — 시도한 순서대로. 각 단계마다 "왜 이걸 먼저 했는지" 한 줄.
4. **핵심 판단** — 지표 선택, 검증 방식, 과적합 경계 등 갈림길에서 무엇을 골랐고 왜.
5. **결과** — 수치와 그래프. 표 + 해석 한 문단.
6. **배운 점** — 다음에 다시 한다면 바꿀 것.

필요하면 절을 합치거나 늘리되, 위 순서(문제 → 데이터 → 접근 → 판단 → 결과 → 배운 점)는 유지한다.

## 3. 문체 규칙

- 한 문단은 **3문장 이내**. 길어지면 끊는다.
- 수식어를 줄인다. "매우", "정말", "굉장히", "성공적으로" 같은 말은 지운다.
- 감상은 마지막 절에만. 본문은 사실과 판단 위주.
- 제목은 명사형으로 짧게. ("데이터 다이어트로 학습 시간 40% 줄이기")
- 같은 말 반복 금지. 앞 절에서 설명한 개념은 다시 풀지 않는다.
- 이모지·느낌표·과장된 표현 금지. (블로그 플랫폼 장식이 필요하면 별도로)
- 숫자는 단위와 함께. 비교는 표로. 표가 3줄을 넘으면 표를 쓴다.

## 4. 문장 예시

- 나쁨: "정말 놀랍게도 GBDT 베이스라인을 적용한 결과 굉장히 좋은 성능을 얻을 수 있었습니다."
- 좋음: "GBDT 베이스라인 AP는 0.31이었다. 피처 엔지니어링 후 0.38로 올랐다."
- 나쁨: "많은 시행착오 끝에 데이터 전처리의 중요성을 깨달았습니다."
- 좋음: "10GB 원본을 그대로 쓰면 코랩 세션이 두 번 끊겼다. 그래서 집계 단위를 미리 줄였다."

## 5. 산출물 형식

- 마크다운(`.md`)으로 낸다. 제목은 `#`, 절은 `##`.
- 코드는 실행 가능한 최소 단위만. 노트북 전체를 붙이지 않는다.
- 이미지·그래프는 `![설명](파일명)` 형태로 자리만 잡고, 어떤 그래프가 필요한지 한 줄로 적는다.
- 글 끝에 "다음 글 후보" 한 줄(선택).

## 6. 작성 후 자체 점검

- [ ] 없는 수치를 만들지 않았는가
- [ ] 각 절이 3문단을 넘지 않는가
- [ ] "왜 그렇게 했는지"가 빠진 단계는 없는가
- [ ] 같은 설명이 두 번 나오지 않는가
- [ ] 제목만 읽어도 글의 흐름이 잡히는가
